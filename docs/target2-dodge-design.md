# 目标二设计：瞄准中双击摇杆闪避（移植 iOS 版闪避）

> 状态：设计稿，待真机验证后实现
> 依赖：目标一（原生宽屏）已完成，未影响输入层

## 1. 目标行为

瞄准状态下，把摇杆向某一方向快速推到底、回中、再推到底（双击式甩杆），角色向该方向闪避。

参考 iOS 版《生化危机4》的闪避手感：

- 必须处于**瞄准**状态才生效（平时推杆是移动，不能误触发）
- 单次手势只触发一次闪避，有冷却，避免连发
- 方向以左右前后四向为主，八向为可选增强

## 2. 现状与约束

### 2.1 输入模型（source/hid.c）

移植层伪造了一个 Zeebo 手柄（IHIDDevice），游戏通过两个接口读输入：

| 接口 | 内容 | 我们的实现 |
|---|---|---|
| `GetNextButtonEvent` | 按键事件队列，元素为 `{id, down, uid, 0, 1}` | `q[]` 环形队列，`hid_poll()` 里按 3DS 按键变化入队 |
| `GetPositionState` | 25 个 u32，槽 1/2 = 左摇杆 xy，3/6 = 右摇杆 xy | `axes[4]`，128 为居中，0..255 |

按键 uid → 游戏内部 id 的换算在 `id_for()`：`uid - B_UP`，拇指键特例 6/7。

**关键：注入输入不需要碰游戏二进制。** 只要往 `q[]` 塞事件、或改写 `axes[]`，游戏就会当成玩家操作。这是整个方案的基础。

### 2.2 无法读取游戏状态

游戏逻辑在 `bio4_brew.mod`（ARM 二进制）里，移植层拿不到"是否在瞄准""是否在换弹"这类状态。所以瞄准判定必须自己推断（见 3.2）。

### 2.3 不能改游戏逻辑

本方案不做二进制 patch。目标一已经证明：只要在移植层做正确的输入/投影映射，就能实现原生效果。

## 3. 关键发现（来自游戏自身数据）

从 `common.h2z` 的 `Bio4_StringLayout.bin` 控制说明里挖到的原文（`re/lang/en.txt` 0x4567 起）：

```
*With weapon ready*
Aim: D-Pad
Action/Attack: {1}
Reload: {2}
Step forward: {^}+{2}
Step right:   {>}+{2}
Step left:    {<}+{2}
Step back:    {v}+{2}
```

以及动作提示表（`3d_base.h2z:sys_param.bin`）里存在：

```
Action: Dodge
Action: Duck
```

**结论：Zeebo 版自带"持枪状态下的方向闪身"（Step）和闪避动作。** 所以闪避不需要新造，只要在正确时机、用正确组合把游戏的 Step 输入送进去。

这比"改二进制加动作"或"退回移动键"都更忠实。

## 4. 方案总览

三层，互相解耦，便于单独调试：

```
  摇杆采样 ──► ① 双击甩杆识别 ──┐
                                 ├──► ③ 动作注入 ──► 游戏
  fov / 瞄准键 ──► ② 瞄准判定 ──┘
```

- **① 手势识别**：纯算法，输入 4 个轴的采样序列，输出"方向 + 触发"事件。可离线单元测试。
- **② 瞄准判定**：优先用瞄准键（KEY_ZR，见 4.2），fov 变化作为兜底与交叉验证。
- **③ 动作注入**：把"向 D 方向 Step"翻译成 pad 事件序列 + 轴覆盖，写入 `hid.c` 的队列。

## 5. 详细设计

### 5.1 手势识别

在 `hid.c` 的 `hid_poll()` 里，每次采样后调用 `dodge_feed(nx, ny, now_ms)`，nx/ny 为归一化到 [-1,1] 的左摇杆值。

参数（先给保守值，真机可调）：

| 名称 | 值 | 含义 |
|---|---|---|
| `EDGE_ON` | 0.80 | 判定"推到底"的阈值（模长） |
| `EDGE_OFF` | 0.35 | 判定"已回中"的阈值 |
| `FLICK_MS` | 260 | 从回中到推到底的最长时间，超过算慢推不算甩 |
| `GAP_MS` | 380 | 两次甩杆之间的最大间隔 |
| `DIR_DOT` | 0.70 | 两次方向的一致性（点积），约 ±45° |
| `COOL_MS` | 700 | 触发后冷却 |

状态机：

```
IDLE
  └─ 模长 ≥ EDGE_ON 且 前一帧 < EDGE_ON ─► FLICK1(记录 dir1, t1)
FLICK1
  ├─ 模长 ≤ EDGE_OFF ─► WAIT2（记录 t_back）
  └─ 超过 GAP_MS 未回中 ─► IDLE
WAIT2
  ├─ 模长 ≥ EDGE_ON 且 (now-t_back) ≤ FLICK_MS
  │     且 dot(dir2, dir1) ≥ DIR_DOT ─► FIRE(dir)
  └─ 超过 GAP_MS ─► IDLE
FIRE
  └─ 交给 ③，进入 COOL_MS 冷却，回 IDLE
```

方向量化：先用四向（上/下/左/右，按 |x| 与 |y| 谁大取主轴）；八向作为开关项，因为斜向 Step 在游戏里未必有对应输入。

伪代码（C，直接可落地）：

```c
typedef struct {
    int state;            // 0 idle 1 flick1 2 wait2
    float dx, dy;         // 第一次甩杆方向
    u32 t_edge, t_center; // 时间戳
    u32 t_cool;
} dodge_t;

// 返回 0..3 = 上/下/左/右，-1 = 无效
static int quantize(float x, float y) {
    if (fabsf(x) > fabsf(y)) return x > 0 ? 2 : 3;   // 右/左
    return y > 0 ? 0 : 1;                            // 上/下
}
```

### 5.2 瞄准判定

优先方案（可靠、零成本）：**瞄准键**。

- 移植层的按键映射是固定的：`KEY_ZR → B_RSHL`（`hid.c` 的 `map[]`）
- 游戏控制说明里"Ready weapon: ZR"，即持枪/瞄准由 ZR 触发
- 所以 `aiming = (held & KEY_ZR) != 0`

兜底方案（交叉验证，也用于将来支持别的按键布局）：**fov 追踪**。

目标一已经在 `gl_Frustumx()` 里拦到了相机视锥。瞄准时游戏会收窄 fov：

```c
// gl.c
float g_fov_now;   // 每帧由 gl_Frustumx 更新 = 2*atan((t-b)/2/n)
```

维护一个慢速基线 `g_fov_base`（只在非瞄准时更新），当 `g_fov_now < 0.88 * g_fov_base` 持续 100ms 判定为瞄准。

两者取或：`aiming = key_zr || fov_narrow`。

> 注意：狙击枪开镜也会让 fov 变窄，但那时 ZR 同样按着，结论一致，不冲突。

### 5.3 动作注入

#### 5.3.1 需要注入什么

游戏要的是"方向 + 闪身键"的组合。两个未知量：

1. 方向用哪一路输入：D-Pad 按键（`B_UP/DOWN/LEFT/RIGHT`）还是左摇杆轴
2. 闪身键是 `{1}..{4}` 中的哪一个（控制方案 TYPE A/B/C/D 各不同）

这两点必须靠模拟器实测确定（见第 6 节），设计上做成可配置：

```c
// 由实测结果填。默认先用"方向轴 + 动作键"的假设
typedef struct {
    int use_dpad;     // 1 = 用 B_UP.. 按键，0 = 用 axes 覆盖
    int step_btn;     // 0 = 不按键，1..4 = B_1..B_4
    int hold_ms;      // 组合保持时长
} step_cfg;
```

#### 5.3.2 注入通道

`hid.c` 增加两个内部接口，只在同一文件内使用：

```c
static void inject_button(u32 uid, bool down);   // 塞进 q[]，然后 sig_raise(sig_btn)
static void inject_axis(int idx, int v, u32 ms); // 定时覆盖 axes[idx]
```

`inject_button` 复用现有队列与信号：

```c
static void inject_button(u32 uid, bool down)
{
    int nt = (qt + 1) & 31;
    if (nt == qh) return;                 // 队列满，丢弃
    q[qt] = (ev_t){ uid, down };
    qt = nt;
    sig_raise(sig_btn);
}
```

#### 5.3.3 时序

```
t+0    : 按下方向（按键或轴覆盖）
t+30   : 按下闪身键
t+180  : 松开闪身键
t+200  : 松开方向
```

约 200ms 的推杆，足够让角色完成一次闪身位移，又不至于变成持续奔跑。

#### 5.3.4 与玩家输入的关系

注入期间玩家的真实输入要**被覆盖而不是叠加**，否则会出现"玩家在推左、注入推右"的抖动。做法：注入期间 `hid_poll()` 末尾跳过 `axes[]` 的正常赋值，直接写入注入值；按键队列里注入事件优先。

### 5.4 集成点

| 文件 | 改动 |
|---|---|
| `source/hid.c` | 新增手势状态机、`inject_button`/`inject_axis`、`hid_poll()` 里接入手势喂入与覆盖逻辑；新增 `hid_dodge_tick()` |
| `source/gl.c` | `gl_Frustumx()` 里记录 `g_fov_now`（约 3 行），供兜底判定 |
| `source/main.c` | 主循环调用 `hid_dodge_tick()`；加一个开关（如 `L+R+Select` 切换闪避开关）便于对比测试 |
| `README.md` | 补一条操作说明 |

不改 `aee.h` 之外的头文件，不动游戏数据。

## 6. 验证计划

分三步，前两步不需要真机。

### 第 0 步：让模拟器能跑（前置）

`re/trace.py` 依赖 `../tools/zeebx-emu/src/brew/aee_helpers.rs` 提取 helper 名字表，本仓库没有这个文件。

替代做法：直接构造 117 项 helper 表，把 `helpers.c` 里已知的实现放到对应下标，其余填通用 stub。这样 trace.py 能启动并记录调用序列。

### 第 1 步：确定 Step 的真实输入（模拟器）

在模拟器里：

1. 启动到游戏内（脚本已支持按键注入 `SCRIPT`）
2. 分别尝试：只推轴 / 只按 D-Pad / D-Pad+各按钮 / 轴+各按钮
3. 观察角色位置变化（`WATCH` 钩子可以盯角色坐标所在内存）

产出：`step_cfg` 的确切取值，写进代码。

### 第 2 步：手势识别离线测试

用合成采样序列跑状态机，覆盖：

- 正常双击 → 触发
- 单次甩杆 → 不触发
- 两次方向不同 → 不触发
- 两次间隔过长 → 不触发
- 冷却期内连按 → 只触发一次

### 第 3 步：真机

编译后看 `log_cia.txt`：新增日志

```
dodge: flick1 dir=right t=12345
dodge: fire dir=right (aim=1)
```

确认瞄准时能闪、不瞄准时不误触发。

## 7. 风险与回退

| 风险 | 影响 | 回退 |
|---|---|---|
| 游戏 Step 需要"方向+键"且按键随控制方案变 | 注入无效 | 读游戏当前方案（难）→ 或直接同时按 1 和 2（无害） |
| 注入的 Step 触发的是"走一步"而非"闪避" | 手感不对 | 缩短保持时长；或改用 `Action: Dodge` 的按键 |
| 瞄准判定误判（狙击开镜） | 无（同样按 ZR） | fov 判定加持续时间过滤 |
| 玩家快速左右推杆被识别成闪避 | 误触发 | 提高 `DIR_DOT`、缩短 `GAP_MS` |
| 注入与真实输入冲突 | 抖动 | 注入期间强制覆盖（5.3.4） |

## 8. 已确认的决策

1. **闪避方向：只做四向**（上/下/左/右）。游戏 Step 文本本身只有四向，斜向没有对应输入。
2. **触发条件：仅在按住瞄准键时生效。** 瞄准键 = `KEY_ZR`（新三）或 `KEY_R`（老三），两者都接受。
   不按瞄准键时推杆就是普通移动，绝不可能误触发。
3. 不额外做开关：条件已经足够严格（必须按住瞄准 + 双击甩杆），再加开关反而增加复杂度。
